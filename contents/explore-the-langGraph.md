# LangGraph로 다시 읽는 AI 프레임워크

## 도입: 로컬 데모는 통과해도, 운영은 왜 무너질까

AI 에이전트를 만들다 보면 가장 먼저 겪는 착각이 하나 있습니다. 바로 “이 정도면 프로덕션에 올려도 되겠지”라는 믿음입니다.

로컬에서는 잘 동작하던 에이전트가, 실제 서비스 환경에 올라가면 다음과 같은 문제에 부딪힙니다.

- **동시 요청이 쌓이면 스레드가 고갈**되고, LLM 호출이 서로 기다리며 전체 지연이 폭증한다.
- **대화 상태가 서버 간에 공유되지 않으면**, 동일 세션이 다른 인스턴스에서 끊겨 버린다.
- **비동기 실행 중 중간에 실패하거나 사용자가 중단하면**, 상태가 반쯤 남아 다음 실행이 깨진다.
- **무한 루프, 재시도 폭주, 타임아웃 누적**으로 오히려 비용과 장애가 커진다.

이런 현상을 보면 단순히 “프롬프트를 잘 쓰는 기술”만으로는 부족하다는 사실이 드러납니다. 실제 운영에서 필요한 건 **모델의 지능**보다 더 근본적인 것, 즉 **파이프라인의 안정성 제어력**입니다.

여기서 LangGraph가 중요해집니다. LangGraph는 단순한 그래프 라이브러리가 아니라, **AI 실행 흐름을 상태와 조건부 전이로 제어하는 워크플로우 엔진**에 가깝습니다. 이는 곧 백엔드 아키텍트가 오랫동안 다뤄온 문제—상태 관리, 병렬 제어, 재시도, 중단/재개, 트랜잭션 분리—와 자연스럽게 연결됩니다.

## 본론 1: LangGraph 핵심 구조를 아키텍처 관점에서 바라보기

LangGraph의 핵심은 아주 단순합니다.

- **Node**: 실제로 무언가를 수행하는 실행 단위
  - LLM 호출
  - 도구 호출
  - 외부 API 요청
  - 사람의 승인 대기
  - 검증/분기 판단
- **Edge**: 상태에 따라 다음 노드로 이동하는 조건부 경로
  - 성공이면 다음 단계
  - 실패면 재시도 또는 예외 경로
  - 사용자 승인 여부에 따라 분기

이 구조를 한마디로 표현하면, LangGraph는 **유향 그래프(DAG/Directed Graph) 기반의 상태 전이 시스템**입니다.

### 1. Nodes: 실행 단위의 책임 분리

백엔드에서 서비스는 보통 각 기능을 작은 책임 단위로 나눕니다. LangGraph도 마찬가지입니다.

예를 들어 주문 처리 에이전트를 만든다면, 다음과 같은 노드로 쪼개는 것이 자연스럽습니다.

- `classify_request`: 사용자 요청을 의도별로 분류
- `fetch_customer_context`: 고객 정보 조회
- `validate_order`: 정책/규칙 검증
- `call_payment_service`: 결제 실행
- `notify_user`: 결과 안내

각 노드는 독립적인 책임을 가지며, 내부 로직은 캡슐화합니다. 이 점은 마이크로서비스의 **서비스 경계 분리**와 닮아 있습니다.

### 2. Edges: 제어 흐름을 상태로 표현한다

중요한 것은 단순히 노드를 나열하는 것이 아니라, **노드 간 전이를 조건부로 제어하는 것**입니다.

예를 들어 결제 실패 시에는 다음과 같은 경로가 생깁니다.

- 결제 성공 → `notify_user`
- 결제 실패 → `compensation` 또는 `human_review`
- 정책 검증 실패 → `reject_request`

즉, LangGraph는 “AI가 생각하는 일련의 판단”을 단순한 함수 호출이 아니라, **상태 머신으로 관리하는 제어 구조**로 바꿉니다.

### 3. 상태(State)라는 중심축

LangGraph의 진짜 핵심은 노드와 엣지 자체보다, **상태(State)가 중심에 있다는 사실**입니다.

상태에는 보통 다음이 담깁니다.

- 현재까지의 대화 히스토리
- 사용자 입력과 중간 결과
- 도구 호출 결과
- 재시도 카운트
- 승인 여부
- 오류/예외 상태

이 상태가 그래프 안을 돌아다니면서, 각 노드가 “이제 무엇을 해야 하는가”를 결정합니다. 운영 관점에서 보면, 이건 결국 **워크플로우 상태를 외부 저장소에 안정적으로 보존하고, 재개 가능한 형태로 관리하는 문제**입니다.

## 본론 2: 아키텍처 관점에서 본 AI 프레임워크의 기술적 본질

LangGraph를 깊게 보면, 그 본질은 단순한 LLM 루프가 아닙니다. 세 가지 축으로 정리할 수 있습니다.

### 1) 유한 상태 기계(FSM) 기반 워크플로우 제어

가장 먼저 보게 되는 것은 **LangGraph가 FSM의 사고방식을 닮았다는 점**입니다.

- 각 노드는 “상태”입니다.
- 각 엣지는 “전이 조건”입니다.
- 그래프 전체는 “상태 전이 시스템”입니다.

이 구조는 우리가 오랫동안 백엔드에서 써 온 **DAG 오케스트레이션 엔진**과 매우 닮아 있습니다.

- Netflix Conductor: 워크플로우를 상태 전이로 표현
- Airflow: 태스크 의존성과 조건부 실행을 DAG로 관리
- BPMN/Workflow Engine: 비즈니스 프로세스를 상태 machine으로 모델링

AI 에이전트가 스스로 판단해서 반복 루프를 도는 것처럼 보이지만, 실은 내부적으로는 **상태 전이와 경계 조건을 제어하는 FSM**입니다.

이 점이 중요합니다. 왜냐하면 실제 운영에서는 “AI가 똑똑하게 판단한다”보다, **무한 루프를 막고 타임아웃을 걸며, 재시도와 분기를 안정적으로 제어하는 능력**이 훨씬 더 중요하기 때문입니다.

#### 왜 Recursion Limit과 타임아웃이 필요한가

AI 워크플로우는 한 번의 LLM 호출로 끝나지 않습니다. 중간에 여러 도구 호출, 재시도, 검증, 승인 대기, 예외 복구가 반복될 수 있습니다.

그 과정에서 다음 문제가 생깁니다.

- 잘못된 분기 조건이 루프를 계속 돌게 만든다.
- 사용자 승인 없이 무한 재시도에 빠진다.
- 긴 실행이 스레드 풀을 점유해 전체 서비스 성능을 망친다.

따라서 LangGraph의 설계는 단순 “AI 호출”이 아니라, **제한된 상태 공간 안에서만 실행되도록 제어하는 시스템**으로 읽어야 합니다.

즉, AI 프레임워크의 본질은 “모델이 똑똑하다”가 아니라, **실행 경로를 안정적으로 제어할 수 있는 워크플로우 오케스트레이터**라는 점입니다.

### 2) 분산 환경에서의 상태 관리와 멱등성

두 번째 축은 분산 환경에서의 **상태 관리**입니다.

로컬에서는 메모리 변수로도 충분히 돌아갑니다. 하지만 서비스가 여러 서버로 확장되면 이야기가 달라집니다.

- A서버에서 시작한 세션이 B서버에서 이어지지 않으면 상태 유실이 발생한다.
- 동시 요청이 같은 세션을 건드리면 레이스 컨디션이 생긴다.
- 중간 상태를 저장하지 않으면 재시도 시 같은 작업이 중복 실행될 수 있다.

이 부분은 분산 캐시와 세션 저장소를 떠올리면 이해가 쉽습니다.

#### Redis/세션 저장소와의 유사성

백엔드에서 세션 상태를 공유하려면 보통 다음 구조를 씁니다.

- 사용자 세션을 Redis 등에 저장
- 서버는 세션 ID만 가지고 상태는 외부에서 조회
- 롤백/재시도 시에도 상태를 기준으로 복구

LangGraph의 Checkpointer나 상태 저장 메커니즘도 이와 같은 철학을 따릅니다.

즉, **실행 상태를 메모리에만 두지 않고 외부에서 관리**한다는 점이 핵심입니다.

#### 동시성 제어와 멱등성

여기서 또 하나 중요한 개념이 나옵니다. 바로 **멱등성(idempotency)** 입니다.

같은 요청을 두 번 보내도 결과가 같아야 하는 설계가 필요합니다. 예를 들어,

- 결제 요청을 한 번만 실행해야 한다.
- “다시 생성” 버튼을 눌렀는데 중복 이메일이 생성되지 않아야 한다.
- 같은 승인 요청이 두 번 처리되지 않아야 한다.

LangGraph가 안정적으로 운영되려면, 상태 저장과 함께 **버전 관리, 낙관적 락, 중복 실행 방지 전략**이 필요합니다.

이건 단순한 AI 라이브러리 문제가 아니라, **분산 시스템에서 상태를 어떻게 일관되게 다룰 것인가**라는 아키텍처 문제입니다.

### 3) 인간 개입 인터럽트(Human-in-the-loop)와 트랜잭션 격리

세 번째 축은 **인간 개입이 들어가야 하는 민감한 워크플로우**입니다.

결제, 삭제, 대금 지급, 관리자 승인과 같은 작업은 자동화만으로는 부족합니다. 이때 LangGraph가 갖는 장점은, 실행을 **중단하고 재개하는 구조**를 자연스럽게 지원한다는 점입니다.

예를 들어 다음 흐름을 생각해 볼 수 있습니다.

1. AI가 결제 승인 여부를 판단한다.
2. 사용자 또는 관리자에게 확인을 요청한다.
3. 승인되면 결제 트랜잭션을 실행한다.
4. 거절되면 보상 절차를 수행한다.

이 구조는 실은 **Saga 패턴**과 매우 닮아 있습니다.

- 실행 중간에 중단 가능
- 승인 결과에 따라 분기 가능
- 실패 시 보상 트랜잭션으로 복구 가능

여기서 백엔드 개발자가 특히 신경 써야 할 것은 **비동기 스레드 반환**과 **커넥션 풀 고갈** 문제입니다.

AI 워크플로우가 길어지면, 대기 중인 작업이 스레드를 계속 점유할 수 있습니다. 이 상태가 쌓이면 DB 커넥션, HTTP 연결, 이벤트 루프가 모두 고갈될 수 있습니다.

그래서 실제 운영 수준에서는 다음이 필요합니다.

- 작업을 비동기 이벤트로 분리한다.
- 장기 실행 상태는 외부 저장소에 기록한다.
- 사용자 응답을 기다리는 동안 스레드를 즉시 반환한다.
- 중단/재개 시점에 보상 로직을 연결한다.

즉, LangGraph는 단순한 “AI의 생각”이 아니라, **장기 실행 업무의 안정적인 중단/재개 경계**를 제공하는 아키텍처 도구입니다.

## 결론: 우리는 이제 ‘AI를 쓰는 개발자’가 아니라 ‘AI 시스템을 설계하는 아키텍트’가 되어야 한다

LangGraph를 이해하는 가장 중요한 관점은 단 하나입니다.

> **AI 프레임워크는 모델의 성능만이 아니라, 운영 중 발생하는 상태 전이와 장애를 제어하는 능력으로 승부한다.**

로컬 데모에서 잘 돌아가는 에이전트는, 실제 서비스에서는 다음을 요구합니다.

- 상태를 안정적으로 저장할 것
- 동시성 경합을 방지할 것
- 무한 루프와 장기 실행을 통제할 것
- 인간 개입과 보상 트랜잭션을 설계할 것

이 관점에서 LangGraph는 단순한 API가 아니라, **AI-native 백엔드 아키텍처를 구현하는 핵심 프레임워크**로 읽어야 합니다.

### 오늘 당장 할 일

- LangGraph 공식 문서와 소스에서 **Checkpointer 메커니즘**을 직접 분석해 보자.
- 상태 저장 방식이 실제로 어떤 방식으로 복구와 재시도를 지원하는지 확인해 보자.

### 이번 주 안에 할 일

- 팀의 복잡한 비즈니스 워크플로우를 **FSM 기반 그래프**로 모델링해 보자.
- “승인 → 실행 → 실패 시 보상” 흐름을 LangGraph 스타일로 분해해 보자.

이제부터는 LangGraph를 “잘 쓰는 기술”이 아니라, **운영 가능한 AI 시스템을 설계하는 사고 프레임**으로 바라보면 됩니다.
